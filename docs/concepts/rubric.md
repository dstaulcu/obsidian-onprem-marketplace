# Concepts: The Review Rubric

_Generated by `om-sync rubric` from `rubric/`. Do not edit by hand; change the rubric files instead._

Rubric **default**, version `default@038466eb4c`. Every review record and report names this version. Any change to a
rule or to the model instructions changes the version, which makes earlier reviews count as stale.

A review has two parts:

1. **Deterministic checks** (below). Plain pattern rules run in code on `main.js`. They are not AI and cannot be
   talked out of a finding. A **high** hit means the verdict can never be `pass`; a **medium** hit is listed for a
   human to judge.
2. **Model review.** Claude Code reads the evidence and applies the instructions further down. The final verdict is
   the worse of the two.

## Deterministic checks

| Check | Severity | Why it matters |
|---|---|---|
| **Runs strings as code (eval)**<br>`eval` | high | eval executes arbitrary text as code, which is the usual way to hide what a plugin really does from review. |
| **Builds functions from strings (new Function)**<br>`new-function` | high | Same risk as eval: code that does not exist in the file until it runs. |
| **Starts other programs (child_process)**<br>`child-process` | high | Lets a plugin run any program on the user's machine with the user's privileges, far outside what a note-taking plugin needs. |
| **Loads code chosen at runtime (dynamic require/import)**<br>`dynamic-load` | high | A literal module name can be reviewed; a computed one can load anything, including code fetched later. |
| **Reaches into Electron internals**<br>`electron` | high | Direct Electron access can bypass Obsidian's API boundaries (windows, shell, clipboard, OS integration). |
| **Uses native bindings (process.binding / .node addon)**<br>`native` | high | Native code cannot be reviewed as JavaScript. |
| **Uses Node file system directly**<br>`node-fs` | medium | Node fs can read and write outside the vault. Plugins should normally use Obsidian's vault API. Listed for a human to judge. |
| **Makes network requests**<br>`network` | medium | Any network call can send vault content out. Many legitimate plugins do this; the referenced hosts are listed so a human can check them. |
| **Touches cookies or credential stores**<br>`credentials` | medium | Reading cookies or the OS credential store is rarely needed by a plugin and is a common theft target. |
| **Looks obfuscated (large encoded blobs)**<br>`obfuscation` | medium | Big encoded strings decoded at runtime are a standard way to hide a payload. |

Also reported on every review (no verdict effect): hosts referenced in the code, and what changed since the
previous version (new check hits, new hosts, size).

## Model instructions

Quoted verbatim from `rubric/review-prompt.md`:

> Look for the following in the plugin, and report each as a finding with its evidence:
>
> - Data exfiltration: vault contents, file names, settings or system information sent anywhere off the machine.
> - Credential or token access: cookies, API keys, OS credential stores, other plugins' stored data.
> - Access outside the vault: reading or writing files elsewhere on disk, launching programs, touching the OS.
> - Remote code loading: fetching code or configuration from the network and executing it.
> - Obfuscation: encoded blobs, string tricks, or logic built so a reader cannot tell what it does.
> - Undeclared network endpoints: hosts the manifest description does not explain.
> - Behaviour that contradicts the manifest description (does more than, or something different from, what it says).
>
> Judging:
>
> - A network call or file access is not a problem by itself. It is a finding when the purpose is unexplained or does
>   not fit what the plugin says it does.
> - Prefer a specific finding with evidence over a vague worry. Quote the code or name the host.
> - Do not guess about code you were not shown. If you only saw excerpts, say so.
>
> Verdicts:
>
> - "pass": nothing concerning in the evidence shown.
> - "findings": there are items a human should look at before this is approved.
> - "fail": clearly malicious or unsafe.

## Fixed safety rules (in code, not part of the rubric)

- Everything from the plugin is treated as untrusted data; instructions inside it are ignored and flagged.
- The model has no tools, runs from an empty directory, and must answer in a fixed schema.
- Malformed model output is recorded as `error`, never as a pass.
- Large bundles get excerpts only, and the report says the coverage is partial.
