# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Purpose

Obsidian's built-in plugin browser can't target a custom registry. This repo provides (1) a **static registry generator** that mirrors GitHub releases from an on-prem GitHub into a folder of files, and (2) an **Obsidian plugin** (`onprem-marketplace`) that browses/installs/updates plugins from that registry. See `docs/README.md` for the admin and client-bootstrap flow.

## Repository & workflow

This is the "home" version. Its remote lives under the `https://github.com/dstaulcu` organization, and it may later serve as the upstream that a work (on-prem) version patches from. Keep org-specific values (e.g. `githubApiBase`, registry URL in `registry.config.json` and the plugin's `DEFAULTS`) as placeholders or config so changes stay easy to carry downstream. Repo name is `obsidian-onprem-marketplace` (`origin` = `https://github.com/dstaulcu/obsidian-onprem-marketplace.git`, branch `main`); the plugin brands as id `onprem-marketplace` in `packages/plugin/manifest.json`. Work is pushed to `main`.

## Commands

npm workspaces (`packages/*`). Run from the repo root:

- `npm install`
- `npm run build` — builds in order: `@om/shared` → `@om/sync` → `@om/cli` → `onprem-marketplace` (order matters; the others depend on shared)
- `npm test` — `vitest run` (tests live in `packages/sync/test/`: `sync`, `signing`, `review`, `reviewers`, `rubric`, `policy`; no linter is configured)
- Single test: `npx vitest run packages/sync/test/sync.test.ts -t "adds versions"`
- Run sync: `node packages/sync/dist/cli.js [registry.config.json]` (needs the env var named by `tokenEnv`; exits 1 if any errors)
- Install plugin into a vault: `node scripts/bootstrap-vault.mjs <vaultPath> <registryUrl> [publicKeyFile] [off|warn|require-signed]`
- `om` CLI (`packages/cli`, built to `packages/cli/dist/om.cjs`): `node packages/cli/dist/om.cjs <init|settings|vaults|list|install|marketplace|config|status|update|verify>` (run `help`; env `OM_REGISTRY`, `OM_PUBLIC_KEY`, `OM_TRUST_MODE`; `--json` for scripting; `om vaults` lists vaults from Obsidian's own `obsidian.json`, and `--vault` takes a path, name or id; `om init` persists registry/key/mode/default vault (or `all`) to a per-user file (`OM_USER_CONFIG` overrides; precedence flag > env > om.config.json > saved); `--all-vaults` loops every vault Obsidian knows; the vault is never guessed). `npm run build:exe` wraps it in `dist/om.exe` (Node SEA via postject; run `npm run build` first). `--registry` also accepts a local folder, which the tests use.
- Signing/review (see `docs/concepts/attestation.md`): `node packages/sync/dist/cli.js keygen keys`, `... review <id@version | --all>` (needs `ANTHROPIC_API_KEY`), `... approve <id@version> --key keys/signing-key.pem`
- Review model: `review.provider` = `claude-code` | `openai-compatible` | `wrapper` (`packages/sync/src/reviewers.ts`); all return untrusted output validated by `review.ts`. Wrapper args are a template (`{provider} {harness} {model} {prompt} {promptFile}`), spawned without a shell.
- Tool-enabled harness: `wrapper.stageFiles` stages plugin files into a temp dir used as the wrapper cwd, re-hashes them after the run, and discards secret-like output (`SECRET_RE` in `review.ts`). Never weaken these checks; the harness sandbox itself is the owner's responsibility.
- Rubric: checks live in `rubric/rules.json` and `rubric/review-prompt.md` (not in code); `node packages/sync/dist/cli.js rubric --write docs/concepts/rubric.md` validates them, runs each rule's examples, and regenerates the readable doc. Rubric version = content hash, so any rule change makes earlier reviews stale.
- Admin service: `node packages/admin/dist/admin.cjs serve --config admin.config.json` (see `admin.config.example.json`); `... passwd <user> --users admin-users.json`. TLS is mandatory unless `allowInsecureHttp` (dev only).
- Rate limits: set the env var named by `tokenEnv` (e.g. `$env:GITHUB_TOKEN = (gh auth token)`); `maxVersions` caps mirrored history

Each package's `build` runs `tsc -p .` (type-check only; `noEmit` in `tsconfig.base.json`) and then bundles with esbuild (sync → `dist/cli.js`, plugin → `packages/plugin/main.js`, CJS, `obsidian`/`electron` external). `dist/`, `registry/` and `packages/plugin/main.js` are gitignored build outputs.

## Architecture

- `packages/shared` — types (`PluginManifest`, `IndexEntry`, `VersionEntry`) and semver/manifest validation, consumed as TypeScript source (`main: src/index.ts`) by both other packages. The registry file format is the contract between sync and plugin, so change types here first.
- `packages/sync` — `syncRegistry(cfg, fetcher)` reads GitHub releases per repo in `registry.config.json`, skips drafts/prereleases, requires release assets `main.js` + `manifest.json` (+ optional `styles.css`), and requires tag (minus `v`) == `manifest.version`. Output layout under `outDir`: `index.json` (latest per plugin), `plugins/<id>/versions.json` (sha256s, newest first), `plugins/<id>/<version>/{main.js,styles.css,manifest.json}`. Properties to preserve: idempotent (a version dir whose `manifest.json` exists is skipped; `manifest.json` is written last as the completion marker), and `rebuildIndex` regenerates `index.json` from disk so previously synced plugins persist. The `Fetcher` is injectable — tests mock it rather than hitting the network.
- `packages/shared/src/registry.ts` — the registry client (`createRegistryClient(base, Transport)`: fetch, `resolveVersion` under the trust policy, `fetchVerified` hash-checked download). Shared by the plugin (`requestUrl` transport) and the CLI (fetch/folder transport); it knows nothing about Obsidian or the filesystem.
- `packages/cli` — `om`, a standalone vault-aware installer for orchestration by external tools (e.g. vault quickstarts). `run.ts` holds the commands, `vault.ts` is the only module that writes a vault (staged writes, manifest last, `community-plugins.json` merged not replaced, `data.json` never touched by install), `transport.ts` is HTTP or local folder. Defaults fail closed (`require-signed`, needs a pinned key). Tests in `packages/cli/test/` build a signed registry folder with `approveVersion`.
- `packages/admin` — optional admin web service (`om-admin`, node built-ins only) for a container deployment: mTLS and/or scrypt-password login behind an `Authenticator` seam (`src/auth/`), one-job-at-a-time sync/review via the shared helpers in `packages/sync/src/jobs.ts` (also used by the sync CLI), read-only status via `state.ts` (verifies with the PUBLIC key only), JSON-lines audit log. Server-side client activity: `activity.ts` tails the nginx JSON access log (`deploy/nginx-om.conf`, parsed strictly by `events.ts`; `tail.ts` cursor uses inode + size + a head fingerprint) into a bounded store persisted with its cursor in one atomic file; `splunk.ts` forwards access + audit events to Splunk HEC at-least-once on its own cursor; `publishStats` writes counts-only `stats.json`. Rubric staleness is `packages/sync/src/rubricdiff.ts`: the rubric version hashes rule id/severity/pattern/flags and the prompt (NOT title/why/examples); the admin keeps a snapshot of each version it sees in `<stateDir>/rubrics`, diffs them, and `staticImpact` re-runs only the deterministic checks (free, no model) to show whether a rubric change moves any result; `POST /api/review {stale:"all"|"changed"}` re-reviews on request only, never automatically. Repositories added from the dashboard live in `<stateDir>/repos.json` (`packages/admin/src/repos.ts`, merged into the sync list by `withNominated`; the admin never edits `registry.config.json`), are validated by `packages/sync/src/nominate.ts` (`checkRepo`: the same acceptance test sync applies, plus refusing a plugin id another repo already provides), and adding one only lets sync mirror it. `syncRegistry` itself refuses to take versions for an id from a repo other than the one that first provided it. The registry landing page is static (`deploy/landing/`, own nginx locations, never in `registry-data`). Admin actions `withdraw`/`hold`/`release`/`revoke` live in `packages/sync/src/manage.ts` (run as audited jobs via `POST /api/manage`; they only tighten clients' view or restore what the publish policy allows, and must never create an approval), shared triage notes are `packages/admin/src/notes.ts` (plain text, append-only JSON lines in the state dir, never in the served registry, never a trust input), and the "Report issue" link is a prefilled GitHub new-issue URL built in the UI (no token, no model output in it). Reviews in the container deployment run in a SEPARATE `reviewer` container (`deploy/reviewer/Dockerfile`; `reviewQueue` in the admin config; `packages/sync/src/reviewqueue.ts`): the admin queues a prompt and treats the raw answer as untrusted (same schema validation and secret filter, so a bad answer is an `error` verdict), writes `review.html`/`review.json` itself, and never holds the Anthropic key; the reviewer sees no registry files and returns only the model answer; a stale heartbeat makes Review all fail fast (503). Keep the admin from ever spawning the model locally when a queue is configured. Activity is inferred from downloads, never trusted for decisions, and clients report nothing. The admin process must NEVER hold the signing key: `POST /api/approve` only queues a request to the separate `signer` container (`deploy/signer/Dockerfile`, `packages/sync/src/signer.ts`, optional compose profile `signer`; no network, read-only registry, re-checks hashes and review itself, logs every decision), and the admin verifies the returned signature with the PUBLIC key and the on-disk hashes before writing `approval.json`. Both workers share the file queue in `packages/sync/src/workqueue.ts`. Docs: `docs/admin.md`; `Dockerfile`/`docker-compose.yml` at the repo root (EXPERIMENTAL: the container ran once on Docker Desktop, but real Splunk, real Obsidian/`om` user agents and real client addresses (Docker shows the bridge IP) are unverified; the registry is the host folder `registry-data/` so `approve` runs on the host; a `logrotate` container (`deploy/logrotate/`) rotates the access and audit logs, retention via `OM_ACCESS_LOG_DAYS`/`OM_AUDIT_LOG_DAYS`/`OM_LOG_MAX_SIZE`, default 14 days / 50M; released only as pre-release tags like `v0.3.0-experimental.2`, which the registry sync skips).
- `packages/plugin` — Obsidian plugin. `registry.ts` fetches registry files via `requestUrl`; `installer.ts` verifies sha256 against `versions.json`, writes into `<configDir>/plugins/<id>`, and reloads/enables via Obsidian's **undocumented `app.plugins`** manager — all such internals are deliberately confined to `installer.ts`; keep it that way. `main.ts` holds the plugin class, marketplace modal and settings tab. The marketplace can't uninstall itself and self-updates when its own repo (id `onprem-marketplace`) is nominated in the registry config.

- `packages/shared/src/attest.ts` — signature verification and the install-eligibility logic (`checkApproval`, `selectVersion`), shared by the plugin and tests. Signed documents are verified over their exact served bytes (ECDSA P-256, raw r||s, base64). The review stage (`packages/sync/src/review.ts`) treats reviewed code as hostile input: Claude Code runs with no tools, deterministic checks in `staticchecks.ts` set a verdict floor the model cannot lower, and the reviewer is injectable so tests never call a model. Never put key material or API keys in config; `*.pem`, `keys/` are gitignored.
- Shell note: writing large files with bash heredocs can fail to parse in this environment; use the file tools or a script file instead. The user's shell is Windows PowerShell 5.1 (no `&&`).
